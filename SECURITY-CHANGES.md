# Security changes

Default changes that affect existing installations, why they were made, and what an existing install must do.
Re-render with `blcli init` and review the diff before applying anything.

## Shared Redis replaced by Valkey

- **The `redis` component now installs Valkey 9.1.3** from the official Valkey chart 0.12.1, pinned by
  `Chart.lock` and a sha256 check. The Bitnami `bitnami/redis:7.2.5` image no longer exists on Docker Hub,
  and the frozen `bitnamilegacy` images are not patched for CVE-2025-49844. The in-cluster address stays
  `<release>-master.<namespace>.svc:6379`, and the password Secret (`redis-shared` / `REDIS_PASSWORD`) is unchanged.
  The upgrade replaces the StatefulSet with a Deployment; data is in an emptyDir and is lost, as on any restart.
- **Commands are now denied by ACL, not renamed.** The default user has `+@all -@dangerous +info -@scripting`.
  Compared with before, `KEYS`, `SORT`, `MONITOR`, `CLIENT LIST`/`KILL`, `SHUTDOWN`, `SAVE`/`BGSAVE`, `MIGRATE`
  and `RESTORE` are also denied (`NOPERM`). Clients that need them set `extraAclRules` (for example `+keys`);
  clients that need Lua set `allowLuaScripting: true`.
- **Internal load balancer off by default and source-limited.** `enableInternalLB` now defaults to `false`.
  An install that uses it must set `enableInternalLB: true` and `internalLBSourceRanges` (client CIDRs) explicitly,
  or the install fails.
- **CPU and memory settings now apply.** `cpuRequest`, `memoryRequest`, `cpuLimit` and `memoryLimit` used to set
  the (disabled) Sentinel container only; they now set the Valkey container (default limit `500M`). Raise
  `memoryLimit` before upgrading if the cache holds more data, or the pod is OOM-killed.

## Administration-services review follow-up

- n9e now allows TCP 8481 to `monitoring-vm` as well as the 8429 writer. The
  vmselect datasource must still be configured in n9e; a write endpoint cannot
  answer alert PromQL queries. Verify an actual query and alert trigger.
- Migration approval is required only for a deployed pre-2.0.0 **wrapper chart**.
  Bytebase wrapper moves from 1.1.1 to 2.0.0; the earlier hardened 1.1.1 still
  needs one reviewed acknowledgment. New installs, routine 2.x upgrades and failed
  2.x retries do not. Unknown/unreadable Helm metadata fails closed. Python 3 is
  now an installer requirement. Retained bootstrap Secret guards are unchanged.
- nginx and ClickHouse use patch versions plus multi-platform manifest digests;
  nginx also drops capabilities, prevents privilege escalation and mounts only
  `/tmp` writable on a read-only root filesystem. Upstream copyright headers in
  rewritten Nightingale DB templates are restored.
- Retired Bytebase args/values (`externalPgEnable`, split PG connection/password
  fields, and obsolete sample/metric CLI options) are removed. Direct legacy
  values now fail explicitly, including `enable: false`; delete those keys and
  use a URI Secret with `metadataDatabase.enabled` instead.

## n9e, Uptrace and Bytebase (maintenance window required)

- **No public entry by default.** n9e uses ClusterIP, Uptrace Ingress is off,
  and Bytebase remains ClusterIP. All three add restrictive NetworkPolicy; allow
  trusted gateways/collectors and required egress explicitly, and verify CNI
  enforcement. Default Uptrace/Bytebase ingress is empty; bootstrap by authorized
  port-forward. Re-render into a fresh directory: blcli may preserve existing files.
- **n9e official sources, patched locally.** The third-party chart dependency is
  replaced by readable official chart 9.1.1 sources with scoped MySQL credentials,
  Redis authentication, random retained bootstrap credentials and Secret config/SQL.
  Built-in node collector/Prometheus and notification script mounts are removed;
  the application runs non-root with a read-only root filesystem. MySQL changes
  from 5.7 to 8.4.13 and Redis to 7.4.12; **never reuse a 5.7 data directory on 8.4**.
  Script notification remains a privileged application capability; see the residual
  risk and migration procedure in `kubernetes/components/n9e/SECURITY.md`.
- **Uptrace overrides now take effect.** Application image/replica settings have
  the required second `uptrace` level. Default image is 2.0.1, matching the old actual
  chart output instead of downgrading it to the previously ignored 1.7.0. Patched
  official chart sources replace known seeds and ClickHouse's hardcoded password
  with retained random credentials, use Secret config, and remove bundled collectors.
  Install the Altinity operator separately. See `kubernetes/components/uptrace/SECURITY.md`.
- **Bytebase 3.24.0 uses external metadata PostgreSQL.** The default creates a
  CNPG cluster with a non-superuser app role; an existing DB can be provided as a
  URI Secret. Embedded metadata PostgreSQL and inline passwords are rejected.
  Bytebase runs as UID/GID 113 with dropped capabilities, no Kubernetes token and
  read-only root filesystem. Removed upstream CLI flags are no longer passed.
  External metadata DB prevents new embedded sample creation; remove existing
  samples separately. Signup restriction needs licensed application configuration
  or a restricted identity gateway; **it is not automatically disabled by Helm**.
  See `kubernetes/components/bytebase/SECURITY.md` before upgrading old data.
- **Existing releases are gated.** Installer upgrades from pre-2.0.0 wrapper charts require
  `BLCLI_SECURITY_MIGRATION_APPROVED=1` after backup/restore and migration rehearsal.
  n9e/Uptrace also refuse upgrades without a migrated `<release>-bootstrap` Secret.
  Editing seeds or that Secret does not rotate passwords already stored in a DB.
  Back up the bootstrap Secret with the data; do not apply offline rendered random
  previews to existing installations. No live environment is changed by this PR.

## Ingress, ArgoCD and monitoring

- **web-ide removed.** The optional `web-ide` component (code-server behind oauth2-proxy) is gone: code-server ran with `--auth none` and any pod in the cluster could reach it without passing the proxy. Existing installs keep running until you remove them: `helm uninstall web-ide -n webide`, back up and delete its PVC, then rotate every credential that was stored in the IDE home volume and the oauth2-proxy client and cookie secrets.
- **ArgoCD deploy key kept out of git.** `kubernetes/init.sh` now writes the key pair to `<workspace>/keys` (or `BLCLI_KEYS_DIR`) instead of `<workspace>/kubernetes/keys`, writes `.gitignore` files for key material, and `gen_ssh_sealed_secrets.sh` pipes the Secret into kubeseal instead of writing `/tmp/ssh-secret.yaml`; the argocd `install` no longer writes `/tmp/argocd-manifests.yaml`. If `git log --all -- keys/` in your kubernetes repository finds the key, treat it as leaked: delete that deploy key on GitHub, generate a new one, add it as a read-only deploy key, re-run `gen_ssh_sealed_secrets.sh` and the argocd install, then run `git rm -r --cached keys/` and purge the history (for example `git filter-repo --path keys --invert-paths` plus a force-push). Also delete any leftover `/tmp/ssh-secret.yaml` and `/tmp/argocd-manifests.yaml`.
- **Dex GitHub client secret moved out of `argocd-cm`.** `dex.config` now references `$argocd-dex-github:clientSecret` (`DexClientSecretName`/`DexClientSecretKey`, or a connector's `clientSecretRef`), and the `DexGitHubClientSecret` arg and any `clientSecret` value in `DexConfig` are no longer rendered. Before applying the new `argocd-cm`, create the Secret (`DEX_GITHUB_CLIENT_SECRET=... ./gen_dex_sealed_secret.sh`, which the argocd `install` also runs, or an ExternalSecret labelled `app.kubernetes.io/part-of: argocd`), or GitHub SSO stops working. The old value sits in your args file, your kubernetes repository history and the live ConfigMap: regenerate the client secret in the GitHub OAuth app and remove it from the args file.
- **ArgoCD 3.5.6, pinned and verified.** The default ArgoCD moves from v2.11.7 to v3.5.6. 2.x gets no fixes for GHSA-9v9p-x54c-58gc, GHSA-fw5c-w8rc-j7fx, GHSA-m3vr-7329-44ww (anyone who can see one application can run commands in, or read files from, the repo-server), GHSA-fmxq-cgp8-87wp (AppProject bypass through delete hooks) and GHSA-j6cw-g6p4-7hch; 3.5.4 and later fix them. `ArgoCDVersion` (`argocd-version`) is now honoured: the `install` script downloads that version's `manifests/install.yaml`, refuses it unless its sha256 matches (the digest for v3.5.6 is built in; any other version or `ArgoCDManifestURL` needs `ArgoCDManifestSHA256`), and applies with `kubectl apply --server-side --force-conflicts`. The verified manifest is kept as `argocd-install.yaml` next to `kustomization.yaml` (a copy that does not match the pin is downloaded again); commit it, since `kubectl delete -k` (`blcli destroy kubernetes`), `kustomize build` and `kubectl diff -k` need it. Replace `argocd-manifest-url: .../v2.11.7/...` in your args file with `argocd-version: v3.5.6`, or the install stops because no digest is pinned for that URL. Upgrading an existing 2.11 install:
  - Read the ArgoCD upgrade notes from 2.11 to 3.5 (`docs/operator-manual/upgrading/` in the argo-cd repository), back up with `argocd admin export -n argocd > backup.yaml`, and upgrade stg first. Three of those notes touch settings this template owns:
    - 3.0 switches resource tracking from the `app.kubernetes.io/instance` label to an annotation. Applications that sync with `ApplyOutOfSyncOnly=true` can be left with orphaned resources: sync each of them once explicitly after the upgrade (or set `application.resourceTrackingMethod: label` in `argocd-cm` to keep the old method).
    - With Dex, RBAC subjects for users move from the `sub` claim to `federated_claims.user_id`. The group bindings this template renders are unaffected, but custom `RBACPolicies` that name individual users must be rewritten.
    - The `repositories` key of the live `argocd-cm` survives `kubectl apply`; the `install` script now removes it.
  - Repositories: 3.x no longer reads the `repositories` key of `argocd-cm`, so ArgoCD loses access to every repository configured there. The new `argocd-cm` drops that key, and `gen_ssh_sealed_secrets.sh` now seals one repository Secret per configured repository (`url`, `type` and `sshPrivateKey`, label `argocd.argoproj.io/secret-type=repository`). Re-run it (the `install` script does when the keys are present) and commit the new `github-ssh-sealed-secret.yaml` before upgrading. A GitHub deploy key reads only one repository, so with several repositories give each `GitRepositories` entry its own key with `sshPrivateKeyFile` (relative to `<workspace>/keys`); entries without one use the default `argocd_github`, which then has to be a machine user's key. The script seals every repository into that one file, so there is no longer a per-key run or extra files to add to `kustomization.yaml`. `GitSSHSecretKey` is gone (3.x requires the key `sshPrivateKey`), and so is the unused `GitHubSSHSecretName`. Repositories you added outside these args need the same Secret.
  - 3.x enforces RBAC on logs, and `update`/`delete` on an application no longer cover its resources; custom `RBACPolicies` may need `logs, get` and `update/*` / `delete/*` rules.
- **ArgoCD reads repositories with a GitHub App by default.** New `GitAuthMethod` (default `github-app`): `gen_github_app_sealed_secret.sh` seals one credential template Secret (`argocd.argoproj.io/secret-type=repo-creds`, `githubAppID`, `githubAppInstallationID`, `githubAppPrivateKey`) that ArgoCD uses for every https repository under `GitHubAppCredsURL`, and the `install` script runs it when the App private key (`<workspace>/keys/argocd_github_app.pem`, `GitHubAppPrivateKeyFile`) is present. GitHub App credentials only work over https, so the default repository URLs (`GitRepositoryURL`, the gitops `SourceRepoURL`/`ApplicationRepo`) are now `https://github.com/...`. Give the App read-only *Contents* and *Metadata* permission and install it only on the GitOps repositories, set `GitHubAppID` and `GitHubAppInstallationID` (the `install` script refuses to run without them), and switch every Application `repoURL` and `AppProjectSourceRepos` entry to the https URL. To keep SSH deploy keys, set `GitAuthMethod: ssh` and keep `git@` URLs everywhere. Either way, `install` refuses a repository URL of the other kind, since ArgoCD matches credentials by URL and that repository would silently get none.
- **ArgoCD AppProject `apps`; `default` project emptied.** Before, every application used the unrestricted `default` project, and `role:org-backend` had every action on it, which amounts to cluster admin (deploy any manifest from any repository into any namespace, including ClusterRoles). The new `appproject.yaml`, applied by `install`, creates `apps` (`AppProjectName`): sources limited to the configured repositories (`AppProjectSourceRepos`), destinations to the application namespace on the local cluster (`AppProjectNamespaces`, default `AppNamespace`), and no cluster-scoped resources. It also empties the built-in `default` project (`RestrictDefaultProject`, default `true`). The gitops templates now render `project: apps` and the GitOps repository as `https://github.com/example-org/gitops.git`, the same URL as the argocd default. **Before upgrading**, move every existing Application to `apps` (set `project: apps` in its manifest), make sure its `repoURL` is listed in `AppProjectSourceRepos` (spelled exactly as in the Application) and its destination namespace in `AppProjectNamespaces`; applications that create cluster-scoped resources need their own AppProject. Until they are moved, set `RestrictDefaultProject: false`, or their syncs fail. With the flag off, `install` re-applies the `default` project as ArgoCD creates it (all sources, destinations and resources), so turning it off also undoes an earlier emptying. If a cluster ever needs that by hand: `kubectl -n argocd delete appproject default` and restart `argocd-server`, which recreates it.
- **ArgoCD RBAC tightened.** The default policies now target the `apps` project: `role:org-admin` manages its applications and reads their logs, clusters and repositories (it can no longer create, update or delete repositories in the UI; repositories come from the sealed Secrets), and `role:org-backend` can view, sync and run actions on them, but not create, edit, override or delete them. `policy.default` is now empty instead of `role:readonly`, so a user who matches no group binding sees nothing (before, everyone who could log in could read every application, including rendered manifests). Update your args file: replace the `RBACPolicies` that name `default/*` with the new defaults, or set `PolicyDefault: role:readonly` to keep the old behaviour.
- **ArgoCD local admin off, GitHub org required.** `argocd-cm` now sets `admin.enabled: "false"` (`AdminEnabled`, default `false`); sign in through Dex SSO, and use `kubectl` (for example `argocd admin` or a port-forward with `AdminEnabled: true` set temporarily) for break-glass access. Delete the leftover `argocd-initial-admin-secret`. The corp project now gets the same Dex and RBAC defaults as prd and stg, since without them nobody could log in. The `install` script refuses to apply when the local admin is off and no Dex connector is configured (nobody could log in), and when a Dex GitHub connector has no `orgs` (`DexConfig` connector `config.orgs`, or `DexGitHubOrgs`): without it any GitHub account can log in. The default `argocd-url` moves from the public `https://app.example.com/argocd` to `https://internal.example.com/argocd`; serve ArgoCD only on an internal host (internal load balancer, VPN or IAP), not on the public product domain.
- **Istio 1.31.3.** The default Istio version moves from 1.27.0 (end of life) to 1.31.3, the shipped args no longer say 1.20.0, and the unused `istio-operator-*` args are gone. The istio `install` now requires an istioctl at least as new as the version it installs and stops if an in-place upgrade would skip more than one minor version. Existing 1.27 installs: upgrade in place one minor version at a time (latest 1.28, 1.29 and 1.30 patch, then 1.31.3, each with the matching istioctl and `spec.tag` set in the rendered `operator.yaml`), or use revision-based canary upgrades, and restart workloads that have sidecars after each step. Istio 1.31 supports Kubernetes 1.32 to 1.37; if you use the Gateway API, install its v1.5 CRDs before 1.30. Change `istio-version: 1.20.0` in your args file to `1.31.3`, or a blcli that honours args would downgrade Istio.
- **Istio auto mTLS on.** `enableAutoMtls` is now `true`, the Istio default (it was `false`). Sidecars now use mTLS towards workloads that have a sidecar; servers stay PERMISSIVE, so clients without a sidecar keep working. No action needed, unless you rely on plaintext between sidecars (for example to inspect traffic); then set `EnableAutoMtls: false`.
- **GitOps app pods hardened.** The base Deployment and StatefulSet now render `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]` and `seccompProfile: RuntimeDefault` on the main container, and `automountServiceAccountToken: false` on the pod and its ServiceAccount; `RunAsNonRoot`/`RunAsUser` are new opt-in parameters. Only newly rendered app manifests change; before you re-render and push an existing app, set `AutomountServiceAccountToken: true` for apps that call the Kubernetes API, and make sure the app needs no Linux capabilities (for example binding a port below 1024) or setuid helpers.
- **Grafana 12.4.13 on chart 11.6.1.** The image moves from 12.3.1 to 12.4.13 (fixes CVE-2026-27880, CVE-2026-27876, CVE-2026-33378 and the other issues patched up to the 2026-10-13 security release). The chart moves from `https://grafana.github.io/helm-charts` 10.4.0 (no longer updated there) to `oci://ghcr.io/grafana-community/helm-charts` 11.6.1, which needs Kubernetes 1.25+ and helm 3.8+; `values.yaml` is refreshed to that chart's defaults. `install` now runs `helm dependency build` and checks the chart sha256 instead of `helm dependency update`, and plugins are pinned to versions. Back up the Grafana PVC before upgrading, and change `image-tag: "12.3.1"` in your args file to `12.4.13`, or a blcli that honours args would keep 12.3.1.
- **Grafana Google login limited to your domain.** `auth.google` now sets `allowed_domains` (and `hosted_domain`) from `hostedDomain`/`hosted-domain`, plus optional `allowedGroups`. Before, any Google account could sign in as Viewer and query every datasource. Set `hosted-domain` to your Google Workspace domain before upgrading (the `example.com` placeholder locks everyone out), then delete accounts from other domains under Administration > Users.
- **Grafana session cookie marked Secure.** `security.cookie_secure` is now `true`. Serve Grafana over HTTPS; users who reach it over plain HTTP can no longer keep a session.

## Data, secrets and infrastructure

- **GKE baseline: Dataplane V2, control-plane allowlist and Secure Boot.** The `gke` module now sets `datapath_provider = "ADVANCED_DATAPATH"` (Dataplane V2 enforces NetworkPolicy natively), renders a `master_authorized_networks` allowlist when the new `masterAuthorizedNetworks` argument is set, and enables Secure Boot on node pools (`enableSecureBoot`, default `true`). Before this, every NetworkPolicy was inert and the control plane accepted connections from any IP.
  - `datapath_provider` and Secure Boot are ForceNew in google provider 5.x. A cluster on the legacy datapath plans a cluster replacement — `deletionProtection` (default `true`) makes that apply fail instead of deleting the cluster. Set `datapathProvider: LEGACY_DATAPATH` to keep the current datapath. Calico (`networkPolicyEnabled: true`) stays opt-in because enabling network policy on a legacy-datapath cluster requires replacing its node pools. Node pools created without Secure Boot plan a node-pool replacement; set `enableSecureBoot: false` to keep them as they are.
  - `masterAuthorizedNetworks` is empty by default, which renders no block and keeps today's behavior. Set it to the CIDRs that should reach the control plane to render the allowlist; the module also disables Google public CIDR access, and the change is in place.
  - Once enforcement is on, the NetworkPolicies this template already ships (ArgoCD and the Helm charts) take effect for the first time. Verify that on a new cluster before rolling it out to existing ones.
  - `masterIpv4CidrBlock` is still not applied by the module: it only matters with a private control-plane block, which is not rendered and would also force cluster recreation.
- **External Secrets Operator chart 2.13.0.** The `external-secrets-operator` chart moves from 0.20.3 (operator v0.20.3) to 2.13.0 (operator v2.13.0). v0.20.3 lets any ExternalSecret read any Kubernetes Secret in the cluster through the `getSecretKey` template function (CVE-2026-22822); 2.13.0 removes that function and fixes the later secret-overwrite advisories. CRDs keep serving and storing `external-secrets.io/v1`, which every manifest here uses, and existing Secrets are not touched. Before upgrading, check that none of your own ExternalSecrets use `getSecretKey`, and that you do not use the Alibaba or Device42 providers (removed in 2.0). Remove a leftover `image-tag: "v2.0.1"` for this component from your args file; it was never applied.
- **`gcp-secret-store` limited to allowed namespaces.** The ClusterSecretStore now has `spec.conditions`: only namespaces labelled `gcp-secret-store-access=allowed`, plus the names in the new `AllowedNamespaces` argument (default `grafana` and `monitoring-vm`), may use it. Before, any namespace could create an ExternalSecret against it and read every Secret Manager secret the store's service account can access. **Before upgrading**, label every other namespace whose ExternalSecrets use this store: `kubectl label namespace NAMESPACE gcp-secret-store-access=allowed`. The juicefs namespace manifest and the redis install script now add the label themselves. ExternalSecrets in a namespace that is not allowed stop refreshing and report an error; the Secrets they already created are kept.
- **Secret Manager accessor grant is additive.** `modules/gke-sm-accessor-sa` used `google_project_iam_binding`, which is authoritative for `roles/secretmanager.secretAccessor`: every apply removed all other project-level holders of that role. It now uses `google_project_iam_member`, which only adds the External Secrets service account. **Before the next `terraform apply`**, in each project directory that uses the module (the `gke` component, or `iam` with `use_secret_manager_accessor`), run `terraform state rm 'module.sm_accessor.google_project_iam_binding.main'`. Without this, Terraform plans to destroy the old binding, and destroying an authoritative binding removes the role from every member listed in it; if that runs after the new member is created, the External Secrets service account loses access and syncing stops until a second apply. After `state rm` the binding stays in place in Google Cloud, the new member resource takes over the same grant, and nobody loses access at any point. Principals that the old binding removed in the past are not restored; their owners must re-grant them. The new optional `smAccessorSecretIdPrefix` (`gke`) and `secret_manager_accessor_secret_id_prefix` (`iam`) arguments limit the grant to secrets whose ID starts with a prefix (IAM condition on `projects/PROJECT_NUMBER/secrets/PREFIX`); the default is empty, so access stays as it is today.
- **Sealed Secrets controller v0.40.0, vendored.** The `sealed-secret` component no longer downloads the v0.32.2 `controller.yaml` from a URL at install time; it applies the v0.40.0 manifest stored in the component (sha256 recorded in `kustomization.yaml`) with the controller image pinned by digest. v0.32.2 is affected by CVE-2026-59341 (controller endpoints usable as a decryption oracle). The upgrade is in place and keeps the existing sealing keys, so existing SealedSecrets keep working. Remove `controller-manifest-url` from your args file; it is no longer used.
- **Redis dangerous commands disabled.** The shared Redis now disables `CONFIG`, `DEBUG`, `MODULE`, `SLAVEOF`, `REPLICAOF` and the scripting commands `EVAL`, `EVALSHA`, `EVAL_RO`, `EVALSHA_RO`, `FUNCTION`, `FCALL`, `FCALL_RO`, `SCRIPT`, in addition to `FLUSHDB` and `FLUSHALL`. The pinned Redis 7.2.5 is affected by CVE-2025-49844 (Lua use-after-free, remote code execution for any client with the password). Clients that use Lua (for example BullMQ or redlock) get `ERR unknown command`; for them, set `allowLuaScripting: true` for the component before upgrading, and only together with a Redis image patched for CVE-2025-49844 (7.2.11, 7.4.6, 8.0.4, 8.2.2 or later). Clients that call `CONFIG` (for example to set keyspace notifications at runtime) must have that setting moved into the server configuration. The upgrade restarts the Redis pod; its data is in an emptyDir and is lost, as on any restart.
- **ParadeDB superuser login off.** The ParadeDB cluster now sets `enableSuperuserAccess: false` (the CloudNativePG default; the chart default was `true`). CloudNativePG then sets the `postgres` password to NULL and deletes the generated `paradedb-superuser` Secret. Anything that logs in as `postgres` must move to the `paradedb-app` credentials or a role declared under `cluster.roles` before upgrading, or set `enableSuperuserAccess: true`. The new `requireTLS` argument (default off) adds a `pg_hba` rule that rejects non-TLS connections.
- **JuiceFS credentials from Secret Manager.** `secret.yaml` (a plain Secret with `postgres://user:pass@...` and `minioadmin`/`minioadmin` defaults, committed with the rendered repository) is replaced by an ExternalSecret that builds the same `juicefs-secret` from the Secret Manager secrets `juicefs-metaurl`, `juicefs-gateway-access-key` and `juicefs-gateway-secret-key` (names set by the new `*SecretName` arguments). The `metaURL`, `gatewayAccessKey` and `gatewaySecretKey` arguments are gone. Before upgrading, create those Secret Manager secrets with the values in use; External Secrets then takes over the existing `juicefs-secret` and keeps it in sync (until they exist it reports an error and leaves the old Secret as it is). Delete the old `secret.yaml` from your kubernetes repository. If real values were ever committed, rotate the metadata database password and the gateway and object storage keys.
- **CDN HTTPS proxy requires TLS 1.2.** The `cdn` component now attaches an SSL policy (profile `MODERN`, minimum TLS 1.2) to each HTTPS proxy; without one Google Cloud accepts TLS 1.0 and 1.1. Applying it is an in-place change. Clients that only support TLS 1.0 or 1.1 can no longer connect; to keep them, set `ssl_min_tls_version` (and `ssl_policy_profile: COMPATIBLE`) on the CDN config.
- **DNSSEC on for public zones.** The `dns` component now enables DNSSEC on public zones that have no `dnssec_config` (in-place change; private zones are not affected). DNSSEC only protects the zone after you publish its DS record at the registrar or in the parent zone; see "DNSSEC for Public Zones" in `terraform/TERRAFORM_PROJECT.md`. To keep a zone unsigned, set `dnssec_config.state: "off"` on it. Never turn DNSSEC off while a DS record is still published.
- **Terraform state bucket locked against public access.** The state bucket created by `terraform/init` now sets `public_access_prevention = "enforced"` (uniform bucket-level access was already on). Applying it is in place; a public (`allUsers`) grant on the bucket, which should never exist, stops working.
