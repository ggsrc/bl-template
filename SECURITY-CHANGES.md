# Security changes

Default changes that affect existing installations, why they were made, and what an existing install must do.
Re-render with `blcli init` and review the diff before applying anything.

## Ingress, ArgoCD and monitoring

- **web-ide removed.** The optional `web-ide` component (code-server behind oauth2-proxy) is gone: code-server ran with `--auth none` and any pod in the cluster could reach it without passing the proxy. Existing installs keep running until you remove them: `helm uninstall web-ide -n webide`, back up and delete its PVC, then rotate every credential that was stored in the IDE home volume and the oauth2-proxy client and cookie secrets.
- **ArgoCD deploy key kept out of git.** `kubernetes/init.sh` now writes the key pair to `<workspace>/keys` (or `BLCLI_KEYS_DIR`) instead of `<workspace>/kubernetes/keys`, writes `.gitignore` files for key material, and `gen_ssh_sealed_secrets.sh` pipes the Secret into kubeseal instead of writing `/tmp/ssh-secret.yaml`; the argocd `install` no longer writes `/tmp/argocd-manifests.yaml`. If `git log --all -- keys/` in your kubernetes repository finds the key, treat it as leaked: delete that deploy key on GitHub, generate a new one, add it as a read-only deploy key, re-run `gen_ssh_sealed_secrets.sh` and the argocd install, then run `git rm -r --cached keys/` and purge the history (for example `git filter-repo --path keys --invert-paths` plus a force-push). Also delete any leftover `/tmp/ssh-secret.yaml` and `/tmp/argocd-manifests.yaml`.
- **Dex GitHub client secret moved out of `argocd-cm`.** `dex.config` now references `$argocd-dex-github:clientSecret` (`DexClientSecretName`/`DexClientSecretKey`, or a connector's `clientSecretRef`), and the `DexGitHubClientSecret` arg and any `clientSecret` value in `DexConfig` are no longer rendered. Before applying the new `argocd-cm`, create the Secret (`DEX_GITHUB_CLIENT_SECRET=... ./gen_dex_sealed_secret.sh`, which the argocd `install` also runs, or an ExternalSecret labelled `app.kubernetes.io/part-of: argocd`), or GitHub SSO stops working. The old value sits in your args file, your kubernetes repository history and the live ConfigMap: regenerate the client secret in the GitHub OAuth app and remove it from the args file.
- **Istio 1.31.3.** The default Istio version moves from 1.27.0 (end of life) to 1.31.3, the shipped args no longer say 1.20.0, and the unused `istio-operator-*` args are gone. The istio `install` now requires an istioctl at least as new as the version it installs and stops if an in-place upgrade would skip more than one minor version. Existing 1.27 installs: upgrade in place one minor version at a time (latest 1.28, 1.29 and 1.30 patch, then 1.31.3, each with the matching istioctl and `spec.tag` set in the rendered `operator.yaml`), or use revision-based canary upgrades, and restart workloads that have sidecars after each step. Istio 1.31 supports Kubernetes 1.32 to 1.37; if you use the Gateway API, install its v1.5 CRDs before 1.30. Change `istio-version: 1.20.0` in your args file to `1.31.3`, or a blcli that honours args would downgrade Istio.
- **Istio auto mTLS on.** `enableAutoMtls` is now `true`, the Istio default (it was `false`). Sidecars now use mTLS towards workloads that have a sidecar; servers stay PERMISSIVE, so clients without a sidecar keep working. No action needed, unless you rely on plaintext between sidecars (for example to inspect traffic); then set `EnableAutoMtls: false`.
