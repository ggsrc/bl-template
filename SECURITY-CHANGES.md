# Security changes

Default changes that affect existing installations, why they were made, and what an existing install must do.
Re-render with `blcli init` and review the diff before applying anything.

## Data, secrets and infrastructure

- **External Secrets Operator chart 2.13.0.** The `external-secrets-operator` chart moves from 0.20.3 (operator v0.20.3) to 2.13.0 (operator v2.13.0). v0.20.3 lets any ExternalSecret read any Kubernetes Secret in the cluster through the `getSecretKey` template function (CVE-2026-22822); 2.13.0 removes that function and fixes the later secret-overwrite advisories. CRDs keep serving and storing `external-secrets.io/v1`, which every manifest here uses, and existing Secrets are not touched. Before upgrading, check that none of your own ExternalSecrets use `getSecretKey`, and that you do not use the Alibaba or Device42 providers (removed in 2.0). Remove a leftover `image-tag: "v2.0.1"` for this component from your args file; it was never applied.
- **`gcp-secret-store` limited to allowed namespaces.** The ClusterSecretStore now has `spec.conditions`: only namespaces labelled `gcp-secret-store-access=allowed`, plus the names in the new `AllowedNamespaces` argument (default `grafana` and `monitoring-vm`), may use it. Before, any namespace could create an ExternalSecret against it and read every Secret Manager secret the store's service account can access. **Before upgrading**, label every other namespace whose ExternalSecrets use this store: `kubectl label namespace NAMESPACE gcp-secret-store-access=allowed`. The juicefs namespace manifest and the redis install script now add the label themselves. ExternalSecrets in a namespace that is not allowed stop refreshing and report an error; the Secrets they already created are kept.
- **Secret Manager accessor grant is additive.** `modules/gke-sm-accessor-sa` used `google_project_iam_binding`, which is authoritative for `roles/secretmanager.secretAccessor`: every apply removed all other project-level holders of that role. It now uses `google_project_iam_member`, which only adds the External Secrets service account. **Before the next `terraform apply`**, in each project directory that uses the module (the `gke` component, or `iam` with `use_secret_manager_accessor`), run `terraform state rm 'module.sm_accessor.google_project_iam_binding.main'`. Without this, Terraform plans to destroy the old binding, and destroying an authoritative binding removes the role from every member listed in it; if that runs after the new member is created, the External Secrets service account loses access and syncing stops until a second apply. After `state rm` the binding stays in place in Google Cloud, the new member resource takes over the same grant, and nobody loses access at any point. Principals that the old binding removed in the past are not restored; their owners must re-grant them. The new optional `smAccessorSecretIdPrefix` (`gke`) and `secret_manager_accessor_secret_id_prefix` (`iam`) arguments limit the grant to secrets whose ID starts with a prefix (IAM condition on `projects/PROJECT_NUMBER/secrets/PREFIX`); the default is empty, so access stays as it is today.
- **Sealed Secrets controller v0.40.0, vendored.** The `sealed-secret` component no longer downloads the v0.32.2 `controller.yaml` from a URL at install time; it applies the v0.40.0 manifest stored in the component (sha256 recorded in `kustomization.yaml`) with the controller image pinned by digest. v0.32.2 is affected by CVE-2026-59341 (controller endpoints usable as a decryption oracle). The upgrade is in place and keeps the existing sealing keys, so existing SealedSecrets keep working. Remove `controller-manifest-url` from your args file; it is no longer used.
- **Redis dangerous commands disabled.** The shared Redis now disables `CONFIG`, `DEBUG`, `MODULE`, `SLAVEOF`, `REPLICAOF` and the scripting commands `EVAL`, `EVALSHA`, `EVAL_RO`, `EVALSHA_RO`, `FUNCTION`, `FCALL`, `FCALL_RO`, `SCRIPT`, in addition to `FLUSHDB` and `FLUSHALL`. The pinned Redis 7.2.5 is affected by CVE-2025-49844 (Lua use-after-free, remote code execution for any client with the password). Clients that use Lua (for example BullMQ or redlock) get `ERR unknown command`; for them, set `allowLuaScripting: true` for the component before upgrading, and only together with a Redis image patched for CVE-2025-49844 (7.2.11, 7.4.6, 8.0.4, 8.2.2 or later). Clients that call `CONFIG` (for example to set keyspace notifications at runtime) must have that setting moved into the server configuration. The upgrade restarts the Redis pod; its data is in an emptyDir and is lost, as on any restart.
- **ParadeDB superuser login off.** The ParadeDB cluster now sets `enableSuperuserAccess: false` (the CloudNativePG default; the chart default was `true`). CloudNativePG then sets the `postgres` password to NULL and deletes the generated `paradedb-superuser` Secret. Anything that logs in as `postgres` must move to the `paradedb-app` credentials or a role declared under `cluster.roles` before upgrading, or set `enableSuperuserAccess: true`. The new `requireTLS` argument (default off) adds a `pg_hba` rule that rejects non-TLS connections.
- **JuiceFS credentials from Secret Manager.** `secret.yaml` (a plain Secret with `postgres://user:pass@...` and `minioadmin`/`minioadmin` defaults, committed with the rendered repository) is replaced by an ExternalSecret that builds the same `juicefs-secret` from the Secret Manager secrets `juicefs-metaurl`, `juicefs-gateway-access-key` and `juicefs-gateway-secret-key` (names set by the new `*SecretName` arguments). The `metaURL`, `gatewayAccessKey` and `gatewaySecretKey` arguments are gone. Before upgrading, create those Secret Manager secrets with the values in use; External Secrets then takes over the existing `juicefs-secret` and keeps it in sync (until they exist it reports an error and leaves the old Secret as it is). Delete the old `secret.yaml` from your kubernetes repository. If real values were ever committed, rotate the metadata database password and the gateway and object storage keys.
- **CDN HTTPS proxy requires TLS 1.2.** The `cdn` component now attaches an SSL policy (profile `MODERN`, minimum TLS 1.2) to each HTTPS proxy; without one Google Cloud accepts TLS 1.0 and 1.1. Applying it is an in-place change. Clients that only support TLS 1.0 or 1.1 can no longer connect; to keep them, set `ssl_min_tls_version` (and `ssl_policy_profile: COMPATIBLE`) on the CDN config.
- **DNSSEC on for public zones.** The `dns` component now enables DNSSEC on public zones that have no `dnssec_config` (in-place change; private zones are not affected). DNSSEC only protects the zone after you publish its DS record at the registrar or in the parent zone; see "DNSSEC for Public Zones" in `terraform/TERRAFORM_PROJECT.md`. To keep a zone unsigned, set `dnssec_config.state: "off"` on it. Never turn DNSSEC off while a DS record is still published.
- **Terraform state bucket locked against public access.** The state bucket created by `terraform/init` now sets `public_access_prevention = "enforced"` (uniform bucket-level access was already on). Applying it is in place; a public (`allUsers`) grant on the bucket, which should never exist, stops working.
